# 本地模型蒸馏落地方案（免 API Key 改造）

> 目标：让新用户**开箱即用、不填任何 API Key** 也能用上 AI 流水线；用户自愿填 DeepSeek Key 时享受云端精度兜底。
> 配套评审材料：对应 README「双层 AI 流水线」与《需求文档》NFR。本文档只做设计，不动代码。

---

## 0. 一页结论

| 问题 | 结论 |
|---|---|
| 为什么要做 | DeepSeek Key 的注册/充值/配置是最大上手门槛；成本反而是小事（重度用户每月几分钱量级） |
| 蒸馏什么 | ① Jev 快判 → 本地小分类器（易，优先做）；② LLM 事件提取 → 本地蒸馏小模型（难，分档做） |
| 怎么集成 | 全部收口在 `getLlmConfig()` 的回落逻辑 + `scoreWithJev()` 内部替换，调用方零改动 |
| 模型怎么来 | 团队离线蒸馏（教师=deepseek-chat，学生=Qwen3 小模型 LoRA），用户侧只下载 GGUF + llama.cpp |
| 最大风险 | 普通笔记本 CPU 推理速度（一批提取 1~3 分钟）、精度回退、低配机内存 |
| 验收标准 | 现有 `pipeline/eval.ts` 6 剧本全绿 + 真实消息盲测集指标不倒退 |

## 1. 现状：Key 与成本分布（代码依据）

### 1.1 三处 LLM 消费 + 一处 Jev 调用

| 调用点 | 位置 | 输入/输出 | 频率 |
|---|---|---|---|
| Jev 快判 | `apps/server/src/pipeline/jev.ts`（端点 `api.typesafe.ai`） | 每批候选 → noul 概率 | 最频繁：每群攒批期间反复分诊 |
| 事件提取 | `apps/server/src/pipeline/extract.ts:336-416` | 30 条候选 + 10 条上下文 + 已有事件 → 事件 JSON | 每群每批 1 次 |
| 桌宠对话 | `apps/server/src/routes/pet-chat.ts:119-152` | 聊天 → ≤60 字回答 | 用户触发 |
| 配置链 | `apps/server/src/ai-settings.ts` → 向导页 `apps/web/src/pages/Setup.tsx` → `data/llm.json` | DeepSeek 必填 + TypeSafe 可选 | 一次 |

### 1.2 成本量级（ honest 账）

- 单次提取约 3k 输入 + 0.5k 输出 token；DeepSeek 现价（以官网为准）下单批成本在 **0.1~0.3 分人民币** 量级。
- 重度用户一天 20~50 批 → **每月几分钱到几毛钱**。桌宠对话同理。
- 结论：**去掉 Key 的核心收益是「零配置、零注册、数据不出本机」，不是省 API 费**。方案取舍应以此为准绳。
- 真正的成本大头在「TypeSafe/Jev 可选 Key」这道可选门槛上：它让快判层对多数用户形同虚设（没填就整层旁路），从而推高 DeepSeek 调用次数。

### 1.3 改造的三个有利条件

1. 所有 LLM 消费方统一走 `getLlmConfig()`（`ai-settings.ts:66-73`）拿 `{baseURL, apiKey, model}` → 换端点只改一处。
2. 提取 prompt 已把**日历查表**和已有事件列表喂给模型（`extract.ts:197-222`），小模型做的是查表与套格式，不是数值推算。
3. 现成验收框架：`pipeline/eval.ts`（6 剧本、精确到时刻的期望）、`pipeline/jev-calibrate.ts`（阈值扫描）、`data/mock/*.json`（剧本库）——蒸馏模型可以直接放进同一套回归体系。

## 2. 总体架构（改造后）

```
QQ 消息 → 规则过滤(本地, filter.ts，不变)
        → Jev 快判：★改为本地 ONNX 分类器（进程内，~40MB，零网络零 Key）
        → 事件提取：★本地蒸馏小模型（llama-server.exe 侧车，OpenAI 兼容 /v1）
                    │  confidence 低 / 用户填了 Key → DeepSeek 云端兜底
        → 桌宠对话：走同一个本地端点（质量敏感度低）
        → 事件合并 reconcile（不变）
```

设计原则：

- **调用方零改动**：`extract.ts` / `pet-chat.ts` 继续用 OpenAI SDK，只是 `baseURL` 指向本地。
- **云端永远可选**：填了 Key 走云（或云为主、本地兜底），没填走本地。向导页 DeepSeek 从「必填」改「可选」。
- **模型不进安装包**：首次启动按需下载（复用 NapCat 组件的下载链路：版本钉定 + SHA-256 + 镜像）。

## 3. 阶段 0：训练数据管道（一切的前提）

### 3.1 数据从哪来

| 来源 | 用途 | 现状 |
|---|---|---|
| `data/mock/` 6 剧本 | 冷启动 + 回归验收 | 已有（约 500 条消息，量级远不够） |
| 合成剧本增强 | 造大量带标注语料 | 需新写生成脚本（见 3.4） |
| 真实群消息（需用户同意） | 最终质量来源 | 需新增记录开关 + 导出脱敏 |

### 3.2 新增 ai_log 落盘（建议直接进账号库）

```sql
CREATE TABLE ai_log (
  id INTEGER PRIMARY KEY,
  kind TEXT NOT NULL,            -- 'extract' | 'jev' | 'pet'
  prompt_system TEXT,
  prompt_user TEXT,
  raw_output TEXT,               -- 模型原始输出
  parse_ok INTEGER,              -- zod 校验是否通过
  attempts INTEGER,              -- 触发重试次数
  model TEXT,
  created_at INTEGER
);
```

落盘点：`extractOnce()` 每次调用后（成功与失败都记，失败样本对训练同样宝贵——它们定义了「输出必须满足什么约束」）。

### 3.3 导出格式（JSONL，每行一个样本）

```json
{"kind":"extract","messages":[{"role":"system","content":"…"},{"role":"user","content":"…"}],"ideal":"{\"events\":[…]}`","ok":true}
```

- `ideal` 生成规则：zod 解析通过的 raw_output 直接用；解析失败但重试成功的，取成功那次；只保留 `confidence ≥ 0.8` 且人工抽查通过的。
- 负样本必须保留：**大多数批次输出是 `{"events":[]}`**，蒸馏数据要还原这个比例（否则学生模型会「手痒」乱造事件）。这是最容易踩的坑。

### 3.4 合成增强

- 用教师模型（deepseek-chat）按模板批量生成新剧本：覆盖改期/取消/多事件交织/口语化时间（「下周三」「下节课后」）/历史补齐拉旧消息等 eval.ts 已知难点。
- 数据量估算：
  - **Jev 分类器**：5k~20k 条标注消息即可（二分类 + 预训练中文编码器起点）。现 jev-calibrate 流程可批量打标。
  - **提取 SFT**：3k~10k 个 (prompt, JSON) 对起步，LoRA 场景下 5k 高质量样本通常可见明显效果。
- 生成成本：5k 对 × ~4k token ≈ 数百万 token，按 DeepSeek 现价 **几元人民币**，忽略不计。
- 合规：批量用 DeepSeek 输出训模型前，核对 DeepSeek 服务条款对「输出用于训练」的约定；学生模型选 Apache-2.0 许可的 Qwen3 系（**避开 Qwen2.5-3B——研究许可**）。

## 4. 阶段 1：Jev 快判本地化（性价比最高，先做）

### 4.1 形态

- 教师：现有 TypeSafe Jev / 或 DeepSeek 按 jev-calibrate 流程产的参考标注。
- 学生：小型中文编码器二分类，推荐 **hfl/rbt3 级别（3 层 RoBERTa，~38M 参数）**：
  - 导出 ONNX + INT8 动态量化后约 **30~50MB**；
  - 运行时用 `onnxruntime-node`（官方 npm 包，Windows x64 预编译，符合「用户机器不装 Python」约束）；
  - 进程内推理，单批 30 条预计 **10~30ms**（对比现在网络请求 + 3s 超时）。
- 输入构造：`[CLS] 群名 [SEP] 上一条消息(可选) [SEP] 本条消息`，对齐现在 `state` 里 group_name / previous_messages / messages 的信息量。

### 4.2 集成点（刻意保持接口不变）

- `jev.ts` 只改 `scoreWithJev()` 内部实现：从「fetch 远端」换成「本地模型推理」，**函数签名、阈值常量（`JEV_DROP_BELOW=0.2` / `JEV_URGENT_AT=0.8`）、退避机制、scheduler 交互全部不动**。
- `jev-calibrate.ts` 换成本地推理后重跑一遍，重新校准两个阈值（本地模型的分数分布和 TypeSafe 不会一致）。
- 配置清理：`TYPESAFE_API_KEY` / `ENABLE_JEV` 语义调整为「本地快判开关」，向导页 Jev 卡片整个删除。
- 交付判据：`jev-calibrate` 报告中「真通知召回 100%（现阈值不丢参考真通知）」+ 本地延迟 p90 < 100ms。

## 5. 阶段 2：事件提取本地化（核心难点）

### 5.1 学生模型选型

| 候选 | 许可 | GGUF(Q4) 体积 | CPU 生成速度(典型核显本) | 预估质量 |
|---|---|---|---|---|
| **Qwen3-1.7B（默认档）** | Apache-2.0 | ~1.1GB | 15~30 tok/s | 格式合规好，复杂改期有错 |
| **Qwen3-4B（推荐主档）** | Apache-2.0 | ~2.5GB | 8~15 tok/s | 大幅接近教师 |
| Qwen2.5-7B-Instruct | Apache-2.0 | ~4.5GB | 4~8 tok/s | 最接近，但低配机不可用 |
| ~~Qwen2.5-3B~~ | ❌ 研究许可 | — | — | 排除 |

决策建议：**默认 1.7B，设置页允许下载 4B 档**；用户填了 Key 则云端优先。

### 5.2 蒸馏训练（团队离线，一次性）

#### 5.2.0 在哪训练：本机路线已验证可行（RTX 5070 Laptop 8GB）

> **执行细节见[《小模型本地训练操作手册》](./本地训练小模型操作手册.md)**（环境搭建、训练脚本参数、OOM 阶梯、评测清单、周末时间表）。本节只留决策结论。

结论先行：**不必租云 GPU**。开发机实测为 RTX 5070 Laptop 8GB + Python 3.13，对两个训练任务都够用：

| 任务 | 显存占用（估） | 本机耗时（估） | 说明 |
|---|---|---|---|
| Jev 分类器（rbt3 级，38M） | 2~3GB | <1 小时 | 全参微调即可，无压力 |
| Qwen3-1.7B QLoRA SFT（5k 样本 × 3 epoch） | 6~7GB | 1~3 小时 | 8GB 刚好，训练时闭掉其他吃显存的程序 |
| Qwen3-4B QLoRA SFT | 7~8GB（贴顶） | 半天量级 | max_seq_len 降到 2048 + 训练样本截断上下文；不稳先回落 1.7B |
| Qwen2.5-7B QLoRA | >8GB，需 offload | 不建议 | 真要训就 AutoDL 租 4090（¥2/时级） |

本机训练的必踩坑（针对 50 系卡 + Windows）：

1. **Blackwell 架构必须装 cu128 版 PyTorch**：装成 cu121 之类旧包会直接报 `no kernel image for sm_120`——50 系第一大坑。
2. **推荐 WSL2 + unsloth**：unsloth 对 Windows 原生支持仍属实验性；LLaMA-Factory 原生 Windows 也可（bitsandbytes 已有 Windows wheel）。
3. **Python 3.13 太新**：用 `uv`/`py` 开 3.11/3.12 虚拟环境再装训练栈，兼容性最稳。
4. **样本太长顶爆 8GB**：本项目提取样本（日历+规则+30 条消息）可达 3~4k token。1.7B @ seq 4096 可跑；4B 必须截断——训练样本把上下文消息砍到 5~10 条即可（教学目标是格式与规则，不是上下文长度）。
5. **Qwen3 思考模式坑**：Qwen3-Instruct 默认先输出思考段（`<think>…</think>`）再给答案，会破坏 `parseExtraction()` 的 `JSON.parse`。对策：蒸馏样本只有最终 JSON（天然无 think 段），训练与部署都显式关思考（llama-server `--jinja` + 关闭 thinking）；**验收时专门检查输出无 think 前缀**。

时间参考（5070 Laptop ≈ 4090 四~六成吞吐）：1.7B 全程（含试跑）一个晚上，4B 一个周末。教师数据生成走 DeepSeek API **不占显存**，可与训练并行。产出物只有两个文件（分类器 `model.onnx` INT8 + 提取模型 `*.gguf` Q4_K_M），在哪训练不影响用户侧架构。

训练流程：

1. 数据：阶段 0 的 JSONL（≥5k 对，含 30% 负样本批次、改期/取消占比与真实分布对齐）。
2. 工具链：LLaMA-Factory（或 unsloth）LoRA SFT，bf16，lr 1e-4、rank 16~32、2~3 epoch；本机 5070 即可（见 5.2.0），或租 4090 数小时（¥10 量级）。
3. 量化导出：合并 LoRA → GGUF `Q4_K_M`；同时保留 F16 以便后续迭代。
4. 验收门（必须全过才算「可发布」）：
   - `pipeline/eval.ts` 6 剧本 × 7 天时间点全绿；
   - 新建「真实消息盲测集」：从真实采集日志抽 30~50 个批次人工标注期望事件，提取准确率 ≥ 教师（DeepSeek）的 90%；
   - JSON 合法率（zod 一次通过率）≥ 99%（SFT 学的是教师的合规输出，天然高；现有 parse-重试逻辑保留兜底）。

### 5.3 运行时集成（复用现成基础设施）

**模型分发**——完全照抄 NapCat 模式：

- 新增 `model.version.json`（钉定 HF 仓库/文件名/SHA-256，与 `napcat.version.json` 同构）；
- 新增 `scripts/fetch-model.mjs`（`fetch-napcat.mjs` 的翻版：官方源 + 镜像回落 + 断点续传 + SHA-256 校验，模型放 `models/`）；
- `llama-server.exe` 本体走 llama.cpp GitHub Release 预编译包（~30MB，同样 SHA-256 钉定）。

**进程托管**——写 `LocalModelManager`，直接以 `apps/server/src/napcat/manager.ts` 为模板：

- 启动：`llama-server.exe -m models/extract.gguf --port <p> --ctx-size 8192 --parallel 1`；
- 健康检查：`GET /health` 就绪后才切端点；
- 崩溃自动重启（复用 manager 的重启/状态机）；
- 应用退出时随之退出；**空闲 10 分钟卸载**（杀进程释放 ~2GB 内存，下批消息来了再拉起——冷启动加载 1.7B 约 2~5s，可接受）。

**配置回落**——唯一需要改的代码收口点（`ai-settings.ts`）：

```
有用户 Key                       → DeepSeek 云端（现状不变）
无 Key 且本地模型就绪             → http://127.0.0.1:<port>/v1，apiKey="local"，model=本地名
无 Key 且本地模型未就绪/下载失败   → 保持现状（AI 未配置），页面上引导下载模型
```

- `extract.ts` / `pet-chat.ts` 不感知差别：llama-server 支持 OpenAI 协议的 `chat/completions`、`response_format: json_object`（内部转 GBNF 约束生成，格式合法性反而更稳）。
- 混合策略（填了 Key 的用户）：紧急消息（`JEV_URGENT_AT` 命中、`QUIET_MS` 收尾路径）走云保即时性，普通攒批走本地省钱；`confidence < 0.6` 的批次结果丢弃并附云端重跑。

### 5.4 性能与资源预算（普通核显笔记本，CPU 推理）

| 项 | Qwen3-1.7B | Qwen3-4B |
|---|---|---|
| 常驻内存 | +1.5GB | +3GB |
| 单批提取延迟（3k prefill + 500 输出） | 40~90s | 1.5~3min |
| 紧急通知延迟（对比现状 ~10s 内可见） | 1~2min | 2~4min |
| 首次下载 | ~1.2GB | ~2.6GB |

缓解手段：

- 本地模式下把 `BATCH` 从 30 降到 15（缩短单批尾部延迟，总吞吐近似）；
- `max_tokens` 从 4096 收紧到 2048（本地输出事件数有限，历史补齐时靠既有的截断拆批逻辑）；
- 空闲卸载 + 下载进度可视化；明确在设置页标注「本地模式较慢，填 Key 可提速提精度」；
- 可选尝试 llama.cpp Vulkan 后端吃核显（收益因机型而异，默认不开）。

## 8. 备选路线（明确不推荐为终态，但可作过渡）

**集中代理池**：团队部署中转服务，内置池化 DeepSeek Key，客户端带安装 ID 限流调用。

- ✅ 当天可上线、用户零配置、精度零回退；
- ❌ 团队持续付费（每百活跃用户每月约几美元量级，可承受但有）；被盗刷/滥用需做限流；违背 README「数据不出本机」卖点；项目停更即全量用户失能。

定位：黑客松评审/演示期可用；正式方案仍以本地蒸馏为准。若做，中转 key 只存服务端，客户端永远拿不到明文。

## 9. 风险登记

| 风险 | 等级 | 对策 |
|---|---|---|
| CPU 推理慢，紧急通知延迟退化 | 高 | 默认 1.7B 档；紧急路径云优先（有 Key 时）；设置页明示；持续评估 4B+Vulkan |

## 10. 需要团队拍板的决策点

1. 默认模型档位：1.7B（快但糙）还是 4B（慢但准）？建议：默认 1.7B + 可选下载 4B。
2. 无 Key 且模型未下载完成期间，AI 卡片显示「下载中」还是允许先跳过？建议显示下载进度、不阻塞扫码连 QQ。
3. 桌宠走本地（质量降级）还是无 Key 时直接禁用？建议走本地，文案弱化为「本地小模型模式」。
4. 是否需要真实消息采集的同意开关（M0 就要定，影响数据合规）。
5. 集中代理池要不要做过渡版（评审时定，影响 M0 优先级）。
