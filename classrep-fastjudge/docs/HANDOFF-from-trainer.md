# 回执 · 给快判脚手架的负责人（来自训练侧，2026-09-30）

回应 `HANDOFF-to-trainer.md`。结论先给：**你们的 TF-IDF 模型赢了，我这条 rbt3-ONNX 路线不该上线。**
下面是同口径实测与几个会直接影响你们下一步的发现。

## 1. 同口径对比：TF-IDF 全面胜出（建议维持现方案）

我在同一批 **115 条真实候选、同一份参考标签**上跑了两种实现
（标签取自 `jev-calibrate --dump` 存档；输入同为生产格式 `群名 [SEP] 上一句 [SEP] 本条`）：

| 丢弃阈值 | 你们的 TF-IDF 召回 / 丢弃率 | 我的 rbt3-ONNX 召回 / 丢弃率 |
|---|---|---|
| 0.05 | **92.0%** / 34.8% | 80.0% / 66.1% |
| 0.20 | **88.0%** / 47.0% | 68.0% / 77.4% |
| 0.45 | **88.0%** / 56.5% | 60.0% / 81.7% |

- 级联（你们当一级、ONNX 复判中间区间）**救回真通知 0 条**，反而会丢掉你们保留的 5 条
  （「老师说考到第四章第二节」「奖学金加分细则，会上要用」等）。
- 原因很直接：我的 Jev 训练数据是**纯合成**的（10k 条 1:3），合成集 AUC 1.0 没迁移到真实分布，
  而你们用的是 mock+synth 混合。**这条经验对提取模型同样成立**，见第 4 条。
- 复现：`python train\tools\head_to_head.py`（需要先 `jev-calibrate --dump <abs path>`）。

## 2. 「真通知召回 100%」这个判据在当前口径下达不到（建议改口径）

阈值扫描（6 剧本 / 115 候选 / 参考真通知 25~30 条）显示：**任何阈值都无法 100% 召回**
（最好 93.3% @0.05）。被漏掉的那几条长这样：

```
0.009  要带琴吗            0.037  第四章也考啊
0.155  接龙：1.小林         0.538  要带电脑吗
```

它们不是"通知"，而是 LLM 提取事件时用到的**上下文碎片**。快判的粒度是**批**（"这批值不值得调 LLM"），
用 `event_sources` 逐条当正样本，会把碎片算进分母，任何单句分类器都拿不到 100%。

**建议**：把基准改成"**至少含一条真通知的批次是否被保留**"——这既符合快判的实际粒度，
也真实反映省下的 LLM 调用。要不要改请你们定，改了我也好把 `JEV_DROP_BELOW` 调到有意义的档位。

## 3. 两个会直接影响线上体验的实测坑

- **常驻 worker 冷启动 6.2 秒**：`Jev：15 次，p50 18ms，p90 24ms，最大 6232ms`。
  默认 `JEV_TIMEOUT_MS=3000`（代码下限 5000）会把**首次请求**判成超时并触发 30s 退避。
  建议启动时预热一次，或把首次请求超时单独放宽到 ≥10s。
- **sklearn 版本**：仓库里 `local-jev-v1.joblib` 由 1.6.1 训练，用 1.9.1 加载会打
  `InconsistentVersionWarning`（分数仍合理）。`requirements.txt` 钉 <1.7 是对的，验收环境别用更高版本。

## 4. 训练侧同类教训（对提取模型）

我同时在做事件提取模型的蒸馏，踩到同一个病根：**合成数据与真实分布有三处系统性偏差**——
噪声 20% vs 真实 78%、字/消息 18 vs 5.9、含时间消息 27% vs 6%。
修好生成模板后四项指标才对齐（详见 `train/BATCH-SHAPE.md`）。
所以你们 handoff 里"用 DeepSeek 对 mock.jsonl 重打 label"这条**优先级很高**，方向是对的。

## 5. 我这边改了两个你们会用到的东西

- `apps/server/src/pipeline/jev-calibrate.ts`：原先**硬性要求 `TYPESAFE_API_KEY`**，
  而产品决策已把 `FASTJUDGE_MODE` 默认设为 `local` —— 默认配置下这个验收门跑不起来。
  已改为"有本地 Jev 即可运行"，并新增 `--dump <path>` 输出逐条候选的分数与标签，
  用来做**跨实现同口径对比**（第 1 节那张表就是这么来的）。
- 训练侧把量化工具放进 `train/tools/`（含"两边必须同样过滤后再比"的口径铁律，
  我自己一度拿过滤后的候选比未过滤的全量消息，得出过夸张的差距）。

## 6. 我的建议（速览）

1. **快判位继续用你们的 TF-IDF 模型**；ONNX 路线先搁置。
2. 若仍想推进 ONNX：先按你们 handoff 的第 1 条**用真实分布重打标签**再训，然后拿同一份 `--dump`
   重跑 `head_to_head.py` 对比 —— 没有这一步不要上线。
3. 认下第 2 条的口径（按批评估召回），否则阈值永远调不到"既省调用又不漏真通知"。
4. 按第 3 条处理冷启动，否则首批必然退避 30 秒。
